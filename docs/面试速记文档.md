# VideoChaosCipher 面试速记文档

> 关键词：RK3588、边缘视频、FFmpeg、硬件优先编解码、CPU 多线程加密、Logistic Map、有界阻塞队列、帧序重排、质量评估、端到端验证。

## 1. 30 秒介绍

这是一个面向 RK3588 边缘设备的视频加扰项目。我用 C++、OpenCV 和 FFmpeg 搭了一个实时视频流水线：视频帧由 FFmpeg 读取，在板端优先尝试 rkmpp/v4l2m2m 这类硬件编解码器，CPU 侧用 Logistic Map 生成混沌序列，对指定时间段的帧做像素级 XOR 加扰。工程上我实现了多线程加密、有界阻塞队列、乱序帧重排、运行统计和单元测试，目标是让 VPU 负责视频编解码，CPU 主要负责加密计算。

## 2. 一分钟介绍

项目背景是边缘摄像头的视频隐私保护。原始视频如果直接传输或存储，泄露风险比较高；但在嵌入式设备上做视频处理又容易被编解码消耗大量 CPU。所以我把系统拆成两个部分：视频 I/O 层用 FFmpeg 封装 `VPUDecoder`/`VPUEncoder`，在 RK3588 上优先找 `h264_rkmpp`、`hevc_rkmpp`、`h264_v4l2m2m` 等硬件编解码器，找不到就自动回退软件编解码；加密层交给 CPU 多线程执行。

加密算法使用 Logistic Map 混沌序列生成伪随机字节，对 BGR 像素逐字节 XOR。流水线是 Reader 读帧、多个 Encryptor 并行加密、Writer 按帧号重排后写出。为了让系统更稳定，我把队列改成有界阻塞队列，支持背压，并增加了解码帧数、加密帧数、写出帧数、队列峰值等统计。当前 WSL 下 15 个单元测试通过，端到端烟测通过；明天上 RK3588 后重点看日志里是否出现 `HW=yes`。

## 3. 项目价值

这个项目适合简历，是因为它不是单纯套算法，而是把算法放进了真实视频工程链路里：视频编解码、帧格式转换、多线程同步、顺序一致性、性能统计、硬件差异和测试验证都会遇到。

实用性要准确表达：它适合作为实时隐私加扰、边缘端视频保护原型和工程演示；如果要做工业级安全，需要改用成熟密码算法和更严谨的密钥管理。如果要做完全可逆的视频归档，需要避免有损编码，或在压缩后的文件/码流层加密。

## 4. 核心架构

```text
Input file / camera
  -> FFmpeg decoder: hardware-first, software fallback
  -> readQueue: bounded blocking queue
  -> N encryptor threads on CPU
  -> writeQueue: bounded blocking queue
  -> writer reorder buffer
  -> FFmpeg encoder: hardware-first, software fallback
  -> output video
```

各模块职责：

| 模块 | 面试说法 |
| --- | --- |
| `crypto.cpp` | 实现 Logistic Map 伪随机序列和逐像素 XOR |
| `SafeQueue.h` | 使用 mutex + condition_variable 实现线程安全队列，支持有界容量和关闭通知 |
| `reader.cpp` | 单线程解码读帧，给每帧编号后入队 |
| `encryptor.cpp` | 多线程消费帧，按时间段判断是否加密 |
| `writer.cpp` | 解决并发导致的乱序问题，按 frame index 顺序写出 |
| `vpu_io.cpp` | 封装 FFmpeg，硬件优先选择 rkmpp/v4l2m2m，失败后回退软件编解码 |
| `stats.h` | 统计 decoded/encrypted/written 帧数、队列峰值和耗时 |

## 5. 为什么要加密

视频数据的价值在于“内容可见”。很多边缘场景里，链路不一定完全可信，例如摄像头到边缘设备、边缘设备到服务器、临时落盘文件、调试人员拷贝数据。加密或加扰的目的就是让没有密钥的人拿到视频也不能直接看到有效画面。

在这个项目里，加密还有一个工程展示价值：视频帧是高吞吐数据，能很好地检验算法是否能放进实时流水线，而不是只在静态图片上跑通。

## 6. 为什么用 FFmpeg

FFmpeg 是成熟的视频多媒体框架，底层包含 demux、decode、scale、encode、mux 等能力。相比直接使用 OpenCV 的 `VideoCapture`/`VideoWriter`，FFmpeg 更容易控制具体编解码器、像素格式、时间戳和硬件加速路径。

项目使用 FFmpeg 的价值：

- 可以显式尝试 `h264_rkmpp`、`hevc_rkmpp`、`h264_v4l2m2m` 等硬件编解码器。
- 可以在硬件不可用时回退到软件路径，保证跨平台开发和测试。
- 可以更细地处理 PTS、time_base、像素格式转换，避免输出视频帧率错误。

## 7. CPU 和 VPU 分工是否完成

代码层面已经完成“CPU 负责加密计算，视频编解码层优先走 VPU”的架构改造。准确表述是：

- CPU：加密计算一定在 CPU 侧执行，多线程并行。
- VPU：代码会优先选择硬件编解码器，但是否实际启用取决于 RK3588 板端驱动、FFmpeg 编译选项、输入视频编码格式和摄像头输出格式。
- WSL/x86：没有 RK3588 VPU，正常回退软件编解码。
- 板端验证：看运行日志中的 `HW=yes/no`，再配合 `scripts/inspect_codecs.sh` 和 CPU 占用确认。

面试时不要说“我保证所有情况下都用了 VPU”，要说“我做了硬件优先和软件回退，并通过运行日志验证实际路径”。这更专业。

## 8. Logistic Map 怎么讲

Logistic Map 公式：

```text
x[n+1] = r * x[n] * (1 - x[n])
```

当 `r` 接近 4 时，它对初值很敏感，可以生成看起来随机的序列。项目把序列值映射成 0-255 的字节流，与视频像素 XOR。XOR 的特点是同一个 key stream 做两次可以恢复原值：

```text
cipher = plain XOR key
plain  = cipher XOR key
```

需要补一句限制：这只是算法层面的可逆。如果中间经过 H.264/H.265 有损编码，像素值被压缩器改变，就不保证逐像素恢复。

## 9. 多线程为什么要重排

Reader 读出来的帧是有序的，但多个 Encryptor 并发处理时，后面的帧可能先处理完。如果直接写出，视频顺序会乱。Writer 使用 `std::map<int, FrameData>` 保存乱序到达的帧，并维护 `nextToWrite`，只有当前帧号到了才写入编码器。

这个点很好讲，因为它体现了你对并发正确性的理解：提高吞吐不能牺牲输出顺序。

## 10. SafeQueue 怎么讲

`SafeQueue` 使用 `std::mutex` 保护队列状态，使用两个 `condition_variable`：

- `notEmpty`：队列非空或关闭时唤醒消费者。
- `notFull`：有界队列未满或关闭时唤醒生产者。

`setFinished()` 用来通知消费者没有新数据了，避免线程永久阻塞。队列容量可通过 `-q` 配置，容量为 0 表示无界；推荐测试和摄像头演示时使用有限容量，例如 `-q 8` 或 `-q 16`。

## 12. 高频面试问答

### Q1：这个项目最核心的亮点是什么？

不是单纯实现一个加密函数，而是把加密放进实时视频流水线：FFmpeg 编解码、多线程加密、有界队列背压、乱序帧重排、质量评估和板端硬件路径验证都做了工程化处理。

### Q2：为什么选择 RK3588？

RK3588 是异构 SoC，有多核 ARM CPU 和视频处理单元 VPU。视频编解码适合交给专用硬件，CPU 适合跑加密算法和线程调度，这样能体现嵌入式平台上的资源分工。

### Q3：VPU 一定能用吗？

不一定。代码已经做了硬件优先尝试和软件回退，但实际是否启用取决于板端驱动、FFmpeg 是否编译 rkmpp/v4l2m2m、输入编码格式等。最终以运行日志和板端监控结果为准。

### Q4：为什么不用 OpenCV 自带 VideoCapture/VideoWriter？

OpenCV 简单，但对底层编解码器、硬件路径、时间戳和像素格式控制不够细。FFmpeg 能明确选择编码器/解码器，也能做更可靠的软件回退和 PTS 设置。

### Q5：这个加密安全吗？

适合作为轻量级加扰和工程原型，不应宣称达到工业级密码学安全。工业场景应使用 AES-CTR、ChaCha20 等成熟算法，并加入密钥管理、认证和防篡改机制。

### Q6：为什么有损编码后不能保证解密完全一致？

XOR 可逆的前提是密文像素没有被改变。但 H.264/H.265 有损压缩会量化和预测，解码后的像素值可能变化。再次 XOR 得到的结果就不是原始帧。要严格可逆，需要无损编码或码流/文件层加密。

### Q7：怎么证明多线程没有写乱帧？

每帧进入流水线时携带 `frameIndex`。Writer 维护 `nextToWrite`，只写当前需要的帧号，提前到达的帧放在 `std::map` 中等待。这样无论加密线程完成顺序如何，输出顺序都稳定。

### Q8：怎么防止队列占满内存？

`SafeQueue` 已支持有界容量。队列满时生产者阻塞，等消费者取走数据后再继续，这就是背压。运行统计会记录队列峰值，便于调参。

### Q9：如何上板验证？

先运行 `scripts/inspect_codecs.sh` 看硬件编解码器是否存在，再运行：

```bash
./build-wsl/video_encryptor input.mp4 output.mp4 0 5 -t 4 -q 16
```

如果用摄像头：

```bash
./build-wsl/video_encryptor /dev/video0 camera_out.mp4 0 10 -t 4 -q 8
```

重点看日志中的 `HW=yes/no`、FPS、CPU 占用和输出视频是否能正常播放。
