# VideoChaosCipher 项目文档

> 当前定位：面向 RK3588/Orange Pi 5 的边缘端实时视频加扰与轻量级加密原型。项目采用 FFmpeg 视频 I/O、多线程流水线和 Logistic Map 混沌序列，让 CPU 主要负责帧级加密计算，让 VPU 在支持的运行环境中承担 H.264/H.265 编解码。是否真正启用 VPU 以运行日志为准。

## 1. 项目背景

摄像头、无人机、边缘网关、实验室监控等场景会持续产生视频流。如果原始视频直接落盘或传输，一旦链路、存储设备或调试环境暴露，画面内容也会暴露。这个项目的目标不是做一个工业级密码产品，而是把“视频处理 + 嵌入式异构计算 + 并发工程 + 加密质量评估”整合成一个可以上板演示、可以讲清楚工程取舍的简历项目。

项目的实用性主要体现在三类场景：

- 实时隐私加扰：边缘设备采集视频后，仅对指定时间段做像素扰乱，让未授权方无法直接观看内容。
- 低成本边缘处理：利用 RK3588 的 VPU 处理视频编解码，CPU 留给加密计算，避免把全部压力压到 ARM CPU 上。
- 教学和工程验证：完整覆盖算法、线程同步、视频 I/O、质量指标、单元测试和上板验证流程，适合作为秋招项目展开讲述。

需要明确边界：当前像素级 XOR 算法本身是可逆的，但如果加密后的帧再经过有损 H.264/H.265 编码，压缩器会改变像素值，因此再次 XOR 不保证逐像素还原。项目当前更适合描述为“实时视频加扰/轻量级加密原型”。若目标是严格可逆归档，应使用无损编码，或在编码后的文件/码流层使用标准密码算法。

## 2. 总体方案

系统把视频处理拆成三个阶段：读帧、加密、写帧。

```text
输入视频/摄像头
    |
    v
VPUDecoder / FFmpeg Decoder
    |
    v
readQueue：有界阻塞队列
    |
    v
N 个 Encryptor 线程：CPU 并行执行 Logistic XOR
    |
    v
writeQueue：有界阻塞队列
    |
    v
Writer：按 frame index 重排并写出
    |
    v
VPUEncoder / FFmpeg Encoder
```

核心分工：

| 模块 | 主要职责 | 当前实现状态 |
| --- | --- | --- |
| CPU 加密 | Logistic Map 生成伪随机字节，对 BGR 像素逐字节 XOR | 已实现，支持指定时间段加密，多线程并行 |
| VPU 编解码 | 在 RK3588 上优先尝试 `h264_rkmpp` / `hevc_rkmpp` / `v4l2m2m` | 已接入 FFmpeg 硬件优先选择；是否命中取决于板端 FFmpeg、驱动和输入格式 |
| 软件回退 | VPU 不可用时使用 FFmpeg 软件编解码 | 已实现，保证 WSL/x86/普通 Linux 能运行和测试 |
| 队列背压 | 防止读/写速度不均导致内存无限增长 | 已实现，有界阻塞队列，`-q` 可配置 |
| 质量评估 | NPCR、UACI、Correlation、Entropy、PSNR/MSE | 已实现单元测试覆盖 |

## 4. 加密实现

加密函数位于 `src/crypto.cpp`。它使用 Logistic Map：

```text
x[n+1] = r * x[n] * (1 - x[n])
```

当参数 `r` 接近 4 时，序列表现出混沌特性。实现中把每次迭代得到的浮点值映射为 0-255 的字节，然后与图像像素的 B/G/R 三通道做 XOR。

同一个 XOR 序列执行两次可以恢复原像素，这是算法层面的可逆性。但视频系统里还要考虑编码器：如果 XOR 后的帧被有损压缩，压缩后的像素已经不是原来的 XOR 结果，所以再次运行同一算法只能近似恢复，不能承诺无损还原。

当前加密支持按时间段选择：程序根据 `frameIndex / fps` 判断当前帧是否在 `[startTime, endTime]` 范围内，只加密指定时间段，非目标时间段直接透传。

## 5. 视频编解码实现

视频 I/O 位于 `src/vpu_io.cpp`，对外暴露 `VPUDecoder` 和 `VPUEncoder`。名字保留了项目早期的 VPU 目标，但当前实现更准确地说是“FFmpeg 视频 I/O 封装，硬件优先，软件回退”。

解码策略：

1. 打开输入文件或 `/dev/video*` 摄像头。
2. 根据输入编码格式优先尝试 RK/V4L2 硬件解码器，例如 `h264_rkmpp`、`hevc_rkmpp`、`h264_v4l2m2m`。
3. 硬件解码器不可用、打开失败或格式不匹配时，回退 FFmpeg 默认软件解码器。
4. 输出统一转换为 OpenCV 常用的 BGR `cv::Mat`，交给 CPU 加密阶段。

编码策略：

1. 优先尝试硬件编码器，例如 `h264_rkmpp`、`h264_v4l2m2m`。
2. 不可用时回退 `libx264` 或 FFmpeg 默认 H.264 编码器。
3. 设置正确的 `time_base`、`framerate` 和 PTS，避免输出视频帧率异常。

运行时日志会打印实际使用的编解码器，例如：

```text
[VPUDecoder] Opened: h264_rkmpp (HW=yes)
[VPUEncoder] Opened: h264_v4l2m2m (HW=yes)
```

如果在 WSL 或普通 x86 Linux 上运行，看到 `HW=no` 是正常现象，说明进入了软件回退路径。

## 6. 并发流水线

项目采用生产者-消费者模型：

| 线程 | 数量 | 作用 |
| --- | --- | --- |
| Reader | 1 | 从 FFmpeg 解码器读取帧，推入 readQueue |
| Encryptor | 1 到 N | 从 readQueue 取帧，判断时间段并执行加密，再推入 writeQueue |
| Writer | 1 | 从 writeQueue 取帧，按 frame index 重排，写入编码器 |

`SafeQueue` 现在支持有界容量。`maxSize == 0` 表示无界；设置为正数时，队列满会阻塞生产者，从而形成背压。这样可以避免摄像头或解码器读得很快、编码器写得较慢时内存持续上涨。

由于多个 Encryptor 线程处理速度不同，输出帧可能乱序。Writer 使用 `std::map<int, FrameData>` 暂存提前完成的帧，只写出 `nextToWrite` 对应的帧，保证输出视频帧序正确。

## 7. 命令行参数

```bash
./video_encryptor <input> <output> <start_time> <end_time> [options]

Options:
  -t, --threads N   加密线程数，0 表示使用 hardware_concurrency
  -q, --queue N     队列容量，0 表示无界，默认 32
  -h, --help        查看帮助
```

示例：

```bash
./build-wsl/video_encryptor input.mp4 output.mp4 0 5 -t 4 -q 16
./build-wsl/video_encryptor /dev/video0 camera_out.mp4 0 10 -t 4 -q 8
```

## 8. 已完成验证

本地 WSL 验证：

- CMake Debug 构建通过。
- Google Test 共 15 个测试通过，覆盖加密算法、质量指标、SafeQueue 基础行为和有界阻塞行为。
- 使用临时生成的 60 帧测试视频完成端到端烟测：程序可读入、加密指定时间段并写出 60 帧输出视频。
- 在 WSL 中没有 RK3588 VPU，日志进入软件编解码回退路径，这是预期行为。

板端待验证：

- `/dev/mpp_service`、`/dev/video*`、`/dev/rga` 是否存在。
- `ffmpeg -codecs` 是否包含 `rkmpp` 或 `v4l2m2m` 编解码器。
- 运行 `scripts/inspect_codecs.sh`，记录实际可用编解码器。
- 运行真实摄像头或 H.264/H.265 文件测试，确认日志里的 `HW=yes` 是否出现。
- 对比软件路径和硬件路径下的 FPS、CPU 占用、端到端延迟和队列峰值。

## 9. 当前效果与简历表述

建议简历表述：

> 基于 RK3588 的边缘端实时视频加扰系统。使用 C++/FFmpeg/OpenCV 构建视频处理流水线，封装硬件优先的视频编解码层，在 RK3588 环境下优先调用 rkmpp/v4l2m2m，失败时自动回退软件编解码；CPU 侧基于 Logistic Map 生成混沌序列，对指定时间段视频帧执行多线程 XOR 加扰；通过有界阻塞队列、帧序重排和运行统计保证实时流水线稳定性，并用 15 个单元测试及端到端烟测验证核心逻辑。

不建议写：

- “已经在所有环境下实现 VPU 硬件编解码”。正确说法是“硬件优先，运行时自动探测，是否启用以日志为准”。
- “H.264 有损压缩后仍可无损解密”。正确说法是“像素级 XOR 算法可逆，但有损编码会破坏逐像素可逆性”。
- “工业级视频加密系统”。当前更适合叫“实时视频加扰/轻量级加密原型”。

## 10. 后续优化方向

1. 板端验证 VPU 实际命中情况，补充真实 benchmark 数据。
2. 增加严格可逆模式：使用 FFV1/PNG 序列等无损编码，或改为文件/码流层 AES-CTR/ChaCha20 加密。
3. 增加摄像头参数配置，例如分辨率、fps、pixel format、输入格式探测。
4. 增加端到端延迟统计和 Prometheus/CSV 输出，方便做性能报告。
5. 若 FFmpeg rkmpp 在板端不稳定，评估直接接入 Rockchip MPP API。
